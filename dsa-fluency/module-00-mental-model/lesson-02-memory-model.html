Memory — why arrays beat linked lists in practice

Big-O hides one of the most important things about real programs: how memory is laid out. Two structures with the same Big-O can be 100× different in wall-clock time. This is the lesson where you stop trusting Big-O blindly and start asking "how is this stored?"

The metaphor: filing cabinet vs. sticky notes

Imagine two ways to keep a list of phone numbers.

Filing cabinet (an array). A long drawer with numbered slots. Slot 0, slot 1, slot 2… each slot is the same size and they're physically next to each other. To get slot 47, you walk to the cabinet, count 47 slots from the front, and pull. Direct addressing.

Scattered sticky notes (a linked list). Each phone number is on a sticky note somewhere in the building, and each note has scrawled on it the location of the next note. To get the 47th, you find the first sticky, read where to go for the second, drive there, read where to go for the third, drive there, and so on. Pointer chasing.

The metaphor

Both structures hold "the same list of numbers." The textbook says "linked lists insert in O(1)." True. But to find the spot to insert, you've already walked the building. The cabinet wins almost every real workload.

Contiguous vs. scattered — what hardware actually rewards

Real CPUs don't fetch memory one byte at a time. They fetch cache lines — typically 64 bytes — and stash them in fast on-chip memory. Reading any byte in that 64-byte block is then nearly free for the next few hundred cycles.

An array of 8-byte integers gets you 8 elements per cache line, all loaded together. Walking the array is mostly free after every 8th element. A linked list, with each node allocated independently somewhere on the heap, costs you a cache miss per node. On modern hardware, a cache miss is hundreds of times slower than a cache hit.

The lie inside Big-O

Big-O counts operations. It assumes every memory access costs the same. Real machines say: an L1 hit is ~1 ns, a main-memory miss is ~100 ns. Two algorithms with the same Big-O can differ by 100× because of cache behavior alone.

Visualize it

The array on the left is contiguous memory — a single block. The linked list on the right is the same data, but each node sits at an unrelated address. Hover over the elements; the array is one allocation, the list is many.

Why list.append is amortized O(1) in Python

Here's the thing that confused everyone in college. Python lists are arrays under the hood. Arrays need a fixed size. So how does append not require copying the whole array on every push?

Answer: Python doesn't allocate exactly the size you need. It allocates more — a "capacity" — and only copies into a bigger allocation when capacity runs out. The standard trick is doubling: when the array is full, allocate one twice as big and copy.

The cost analysis: across n appends, the copies sum to n + n/2 + n/4 + … = 2n. Total work is O(n). Per append on average: O(1). That's amortized O(1): any single append might be expensive, but the average over a sequence is constant.

The two questions to ask about every data structure

  1. How is it laid out in memory? Contiguous (cache-friendly) or scattered (pointer-heavy)?
  2. What does each operation cost — worst, average, amortized? Don't just say "O(1)" — say which O(1).

Interview reality

"Why use an array over a linked list?" is a classic warm-up. The textbook answer is "random access is O(1)." The L5 answer adds: "and contiguous memory means cache-friendly traversal — in practice, even an O(n) array operation is often faster than the equivalent linked-list operation because of cache locality."

The exception: when linked lists actually win

Don't completely write linked lists off. They earn their keep when:

  • You insert and remove from known positions in the middle of the structure with O(1) cost — and that "known position" was given to you as a node reference, not an index. (LRU caches do this.)
  • You need persistence (functional programming): nodes can be shared between versions of the list.
  • You need to splice two long sequences together cheaply — O(1) instead of O(n + m) on arrays.

For interview problems, you'll see linked lists almost exclusively as a way to test pointer-manipulation skills, not because they're the right tool. We'll go deep on that pattern in Module 3.
