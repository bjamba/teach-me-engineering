⚙️ GitHub Actions runner at home

Free CI on your beefy machine. Faster than GitHub-hosted runners for big builds. Reach internal services on your tailnet (private package registries, internal APIs) directly.

Gallery Dev Workflow Advanced Half-day Prereqs: M3 + a GitHub repo

Why this project

GitHub-hosted runners have minute limits, burn money on private repos, and can't reach your internal infrastructure. A self-hosted runner on a beefy machine you already own is dramatically faster and free, and being on your tailnet means it can pull from private package registries and internal services without exposing them.

Who this helps

  • You have a private repo with non-trivial CI you'd rather not pay for
  • You have an underused beefy machine at home (Mac mini, gaming PC, server)
  • Your CI needs to reach private internal services (DBs, package registries) — easy if both are on the tailnet
  • You want to avoid sending source code through GitHub-hosted runners

What you get

  • A self-hosted runner registered with your repo, available 24/7
  • Zero per-minute CI cost on private repos
  • Access to tailnet-internal services (databases, registries) from CI jobs
  • Often dramatically faster builds (no shared queue, no spin-up)

Runner registers with GitHub via outbound API; jobs run on your host. Tailnet membership lets the runner reach private internal services (DB, registry, secrets) without exposing them publicly.

Prerequisites

  • Tailscale running on the host (M3)
  • A GitHub repository where you have admin rights to add a runner
  • Linux/macOS host with a stable network and disk space for build artifacts

Steps

Install the runner ~10 min

Follow GitHub's official runner setup: repo Settings → Actions → Runners → New runner. They give you a script — pre-baked with a token, registers the machine.

Run it as a service ~5 min

cd ~/actions-runner
sudo ./svc.sh install
sudo ./svc.sh start
sudo ./svc.sh status

Auto-starts at boot. Works without you logged in.

Tag the host and ACL it ~3 min

If Tailscale is already running on this host, you're set. Tag it tag:ci and write an ACL granting it source access only to specific destinations:

{
  "tagOwners": { "tag:ci": ["group:adults"] },
  "acls": [
    { "action": "accept", "src": ["tag:ci"], "dst": ["tag:registry:*", "tag:db:5432"] }
  ]
}

Use it in workflows ~2 min

jobs:
  build:
    runs-on: self-hosted    # instead of ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cargo build --release

For more isolation: ephemeral container runners +30 min

The basic runner runs jobs on the bare host — your secrets and disk state persist between jobs. For real isolation, use the Actions Runner Controller on Kubernetes, or roll ephemeral Docker runners.

Each ephemeral runner uses an ephemeral Tailscale auth key (M3L6) — joins the tailnet, runs the job, exits, removes itself.

Verify

  • The runner appears as "Idle" in repo Settings → Actions → Runners
  • A workflow with runs-on: self-hosted runs on it (check the job log)
  • The runner can reach a tailnet-internal service from a job
  • The runner survives a host reboot (kicks back to "Idle" automatically)

Common issues

  • Runner offline after reboot — confirm ./svc.sh install was run, not just ./run.sh.
  • Permission denied on tailnet resources — your ACL doesn't grant tag:ci the right destinations.
  • Builds fail with disk full — runners don't auto-clean. Use actions/cache sparingly or add a periodic cleanup job.

Caveats

  • Don't enable on public repos unless you really know what you're doing — anyone who can open a PR can run code on your runner.
  • Lock down the ACLs — the runner is essentially a guest with code-execution privileges.
  • Job logs are public on GitHub — be careful with what you echo.

Where this leads

  • Funnel a webhook receiver for repository events
  • Combine with a private package registry on your tailnet (e.g. self-hosted Verdaccio for npm)
  • Run a fleet of ephemeral runners using Tailscale ephemeral auth keys
