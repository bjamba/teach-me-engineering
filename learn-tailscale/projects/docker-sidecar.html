🐳 Tailscale + Docker sidecar

The reusable pattern for putting any container on your tailnet without publishing ports to your LAN. Once you know this, every other Docker-based project (Jellyfin, Vaultwarden, Pi-hole, Home Assistant) follows the same recipe.

⭐ Core Dev Workflow Intermediate ~1 hr Prereqs: M4 (Toolbox)

Why this project

Every Dockerized service ships with `ports: ["8080:80"]` examples that publish the service to your host's LAN. Anyone on your home wifi can hit it; if you accidentally allow incoming on your router, the world can. The sidecar pattern fixes this: each container becomes its own tailnet device, reachable only over your tailnet, with no LAN exposure.

This is genuinely the answer for most "how do I get this Dockerized service onto my tailnet" questions. Same recipe, different service — once you've internalized the pattern, every container project becomes a copy-paste exercise.

Who this helps

  • You self-host services in Docker and want them tailnet-only by default
  • You're already comfortable with docker-compose and want a reusable template
  • You're about to start the Jellyfin / Vaultwarden / Home Assistant projects and want to learn the underlying pattern first

What you get

  • A working private nginx exposed at https://ts-nginx.tail-abc.ts.net
  • A reusable docker-compose template you'll apply to every other containerized service
  • Each container appears as its own tailnet device, ACL-controllable independently
  • Zero ports published to your host's LAN — the LAN can't see these services even though they're running on a LAN-connected host

Prerequisites

  • Docker + docker-compose installed on the host
  • M4 toolbox concepts (tags, Serve, auth keys)
  • Permission to generate Tailscale auth keys for your tailnet

Mental model

Run a Tailscale container as a sidecar to your service container. Both share a network namespace, so the service is reachable on the tailnet via the sidecar's tailnet identity — without ever publishing ports to your host's LAN. From the tailnet's perspective, the sidecar IS the service. From the service's perspective, the sidecar is just localhost.

Steps

Generate an auth key for the sidecar ~3 min

Admin console → Settings → Auth keys → Generate auth key.

  • Reusable: off (single-use; you'll generate fresh per container)
  • Ephemeral: on (so when the container stops, the device cleans itself up)
  • Pre-authorized: on (so you don't have to manually approve)
  • Tags: pick or create tag:container (declare in tagOwners first if needed)

Copy the key. Looks like tskey-auth-XXXXX.

Write a docker-compose.yml ~5 min

Save this as docker-compose.yml on your home server:

services:
  ts-nginx:
    image: tailscale/tailscale:latest
    hostname: ts-nginx
    environment:
      - TS_AUTHKEY=${TS_AUTHKEY?required}
      - TS_EXTRA_ARGS=--advertise-tags=tag:container
      - TS_SERVE_CONFIG=/config/serve.json
      - TS_STATE_DIR=/var/lib/tailscale
      - TS_USERSPACE=false
    volumes:
      - ts-state:/var/lib/tailscale
      - ./serve-config.json:/config/serve.json
      - /dev/net/tun:/dev/net/tun
    cap_add:
      - net_admin
      - sys_module
    restart: unless-stopped

  nginx:
    image: nginx:alpine
    network_mode: service:ts-nginx
    depends_on:
      - ts-nginx
    restart: unless-stopped

volumes:
  ts-state:

The key trick is network_mode: service:ts-nginx on the nginx container — it shares its network namespace with the Tailscale sidecar.

Add a Tailscale Serve config ~2 min

Save this as serve-config.json alongside the compose file:

{
  "TCP": { "443": { "HTTPS": true } },
  "Web": {
    "${TS_CERT_DOMAIN}:443": {
      "Handlers": { "/": { "Proxy": "http://127.0.0.1:80" } }
    }
  }
}

Bring it up ~3 min

export TS_AUTHKEY="tskey-auth-XXXXX"
docker compose up -d

Check docker compose logs ts-nginx — you should see "Success." and the device's tailnet IP.

Visit the service ~1 min

From any tailnet device, navigate to https://ts-nginx.tail-abc.ts.net. Nginx welcome page over HTTPS, valid cert. Check the admin console — ts-nginx appears as a tagged device.

Apply the template to anything else ~5 min per service

Reuse the pattern. The shape is:

services:
  ts-{name}:
    image: tailscale/tailscale:latest
    hostname: ts-{name}
    # ... same Tailscale config ...
  {name}:
    image: {your-service-image}
    network_mode: service:ts-{name}
    # ... your service's config ...

Generate a fresh auth key per service. Adjust the Serve config to point to whatever port your service listens on (Jellyfin = 8096, Grafana = 3000, etc.). Done.

Verify

  • https://ts-nginx.tail-abc.ts.net loads from any tailnet device with a valid cert
  • Curling the host's LAN IP on port 443 fails — the service isn't published to the LAN
  • Admin console shows ts-nginx as a tagged device
  • docker compose down followed by checking the admin console: the device removes itself (ephemeral)

Common issues

  • Sidecar logs say "permission denied" on /dev/net/tun — make sure cap_add: [net_admin, sys_module] is set, or switch to TS_USERSPACE=true.
  • Cert provisioning fails — HTTPS Certificates must be enabled in admin → DNS first.
  • Service container starts but isn't reachable — confirm network_mode: service:ts-{name} matches the sidecar's service key.

Variations

  • Funnel mode: add "AllowFunnel": {"${TS_CERT_DOMAIN}:443": true} to the serve config and ensure Funnel is enabled in your tailnet policy. The container goes public.
  • Multiple services on one device: add more proxies to the Serve config, all pointing to different localhost ports.
  • Userspace mode: set TS_USERSPACE=true if you can't grant net_admin.
