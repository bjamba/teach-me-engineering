🤖 Local AI gateway — the private API

Run an LLM on your beefiest machine; expose it as a private OpenAI-compatible API on your tailnet. The minimum viable private AI: scripts, editor extensions, anything that speaks the API can hit it from any device you own.

⭐ Core AI/ML Intermediate ~45 min Prereqs: M3 + M4L3 (Serve)

Why this project

Cloud LLM APIs cost money and see your prompts. Local LLMs are free and private — but until now, hard to access from your phone or while traveling. With Tailscale Serve in front, your home AI rig becomes a private API that follows you everywhere.

This first project is the foundation: get the engine running, get a stable HTTPS URL, prove you can hit it from any tailnet device. Two later projects layer a chat UI and multi-user features on top — but they all share this same engine + Serve setup, so the work you do here pays compounding interest.

Who this helps

  • You already use ChatGPT/Claude/Gemini and want a free, private alternative for the 80% of asks that don't need a frontier model
  • You have a beefy machine at home that's underutilized
  • You'd rather your prompts stayed on hardware you own
  • You want to plug your own private API into editor extensions (Continue, Aider, Cursor) without paying per token

What you get

  • Your choice of engine (Ollama for easy mode, llama.cpp if you want closer to the metal) running on your home rig
  • An OpenAI-compatible API at https://ai-rig.tail-abc.ts.net
  • One-line curl from any tailnet device gets you a real LLM response
  • The plumbing in place for the next two projects (chat UI, multi-user proxy)

Prerequisites

  • Tailscale running on the machine that'll host the engine (M3)
  • Tailscale Serve concepts from M4L3
  • HTTPS Certificates enabled in admin → DNS

Mental model

What you're building in this project is the bottom half of a four-layer stack. Projects 2 and 3 add the optional pieces on top.

For this project: clients → Serve → engine → models. Project 2 adds Open WebUI between Serve and the engine. Project 3 adds LiteLLM as a proxy.

Engine comparison

Both engines speak OpenAI-compatible APIs, so the rest of the project (and projects 2 and 3) work with either. Pick the one that fits your taste.

Default in this project: Ollama. The walkthrough also has a llama.cpp tab. vLLM is in the Variations section.

Hardware notes

  • Minimum: any computer with 16GB RAM can run smaller models (Llama 3.2 3B, Phi-3 Mini). CPU-only is fine, just slow.
  • Comfortable: Apple Silicon Mac with 32GB+ RAM, or a Linux box with an Nvidia GPU (8GB+ VRAM).
  • Excellent: a 4090 or M3 Max. You can run 70B models at usable speeds.

Steps

Six steps. Install, fetch a model and run, open the engine to proxied requests (Ollama only — its default host-header check blocks Tailscale Serve), expose via Serve, verify from another device, lock down with ACLs.

Pick an engine and install ~5 min

Pick the tab that fits. The choice affects only the next two steps; everything from step 4 onward is identical for both.

Ollama is the friendliest path. Auto-handles model downloads, runs as a service, single command per model. Wraps llama.cpp underneath but hides the complexity.

# Linux:
curl -fsSL https://ollama.com/install.sh | sh

# macOS / Windows: download from ollama.com/download

llama.cpp gives you the underlying engine directly. Better for: custom GGUF model files, specific quantization choices, minimal abstraction.

# macOS:
brew install llama.cpp

# Linux: build from source or use the prebuilt releases
# https://github.com/ggerganov/llama.cpp/releases

Fetch a model and run the server ~10–30 min depending on download speed

Now that the engine is installed, you need actual model weights. Start small to verify the pipeline before you wait on a 40GB download.

# Pull a small model first to test:
ollama pull llama3.2:3b

# Then try a larger one when you're confident:
ollama pull llama3.1:8b           # 4.7 GB · good general model

# Verify locally:
ollama run llama3.2:3b
>>> what's the airspeed velocity of an unladen swallow?
# /bye to exit. Ollama installs as a service that auto-starts —
# the OpenAI-compatible API is now listening on localhost:11434.

Browse ollama.com/library for more models.

llama.cpp uses GGUF files. Download from Hugging Face — search any model name + "GGUF" and you'll find quantized variants:

mkdir -p ~/models && cd ~/models
huggingface-cli download bartowski/Meta-Llama-3.1-8B-Instruct-GGUF \
  Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf \
  --local-dir .

# Start the server:
llama-server \
  -m ~/models/Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf \
  --host 0.0.0.0 \
  --port 8080 \
  -c 4096

# Verify:
curl http://localhost:8080/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "llama-3.1-8b",
  "messages": [{"role":"user","content":"hello"}]
}'

For long-running, wrap as a systemd service. Default port is 8080 — substitute that everywhere we mention 11434.

Open the engine to the proxied hostname ~3 min · Ollama only

Skip this step if you're on llama.cpp — it already binds to 0.0.0.0 per step 2.

Ollama by default only accepts requests where the HTTP Host header is localhost, 127.0.0.1, or 0.0.0.0. That's a sensible default for a desktop app, but it means a request proxied through Tailscale Serve (which carries Host: ai-rig.tail-abc.ts.net) gets rejected with a 403 Forbidden. You'd see the TLS handshake succeed, then a stark empty 403 — like the request never reached an LLM at all.

Set OLLAMA_HOST=0.0.0.0:11434 as an environment variable for the Ollama service. It relaxes the host-header check (the binding to all interfaces is harmless because Tailscale Serve is your only external path).

sudo systemctl edit ollama
# In the editor, paste:
[Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"

# Save, then:
sudo systemctl daemon-reload
sudo systemctl restart ollama
launchctl setenv OLLAMA_HOST "0.0.0.0:11434"
# Then quit and reopen the Ollama app from Applications.

System Properties → Environment Variables → add a user variable OLLAMA_HOST = 0.0.0.0:11434. Restart Ollama.

Confirm Ollama is listening on all interfaces and the env var took:

curl http://0.0.0.0:11434/api/tags
# Should return your model list. "Connection refused" means the env var didn't apply — restart Ollama.

Expose via Tailscale Serve ~3 min

The engine is alive and accepts requests for any host. Now put it on your tailnet so other devices can reach it.

# Ollama:
sudo tailscale serve --bg http://localhost:11434

# llama.cpp (port 8080):
sudo tailscale serve --bg http://localhost:8080

Output: a URL like https://ai-rig.tail-abc.ts.net. Tailscale grabs a Let's Encrypt cert for that hostname and reverse-proxies to your engine.

Whenever you're unsure what's currently being served: sudo tailscale serve status. sudo tailscale serve reset clears everything and starts over.

Verify from another device ~3 min

From your laptop or phone (any tailnet device that isn't the engine host), call the API:

curl https://ai-rig.tail-abc.ts.net/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "llama3.2:3b",
    "messages": [{"role":"user","content":"Why is the sky blue?"}]
  }'

Wait a few seconds, get a JSON response. This is the moment the project pays off. Your home rig is doing the inference; your other device is just sending the prompt over the tailnet.

While you're at it: try this same call over cellular (turn off wifi on your phone), or while tethered to a hotspot. Tailscale's NAT traversal handles it; the URL doesn't change.

Lock down with ACLs ~3 min

Tag the AI host tag:ai in your tailnet's policy and restrict access to family-only:

{
  "tagOwners": { "tag:ai": ["group:family"] },
  "acls": [
    { "action": "accept", "src": ["group:family"], "dst": ["tag:ai:443"] }
  ]
}

Now even if a tagged container or guest user is on your tailnet, they can't reach the API unless they're family.

Verify

  • curl /v1/models from a different tailnet device returns your model list
  • The same call works over cellular or hotspot wifi (NAT traversal is doing its thing)
  • Generation responses come from your machine (CPU/GPU usage spikes on the host)
  • An off-tailnet device gets nothing when it tries the URL

Common issues

  • 403 Forbidden from a tailnet curl, but TLS succeeded — Ollama's host-header check rejecting the proxied hostname. Step 3 above is the fix; if you skipped it, do it now and restart Ollama. Verify with curl http://0.0.0.0:11434/api/tags on the host (should return your model list).
  • Cert provisioning fails — make sure HTTPS Certificates is enabled in admin → DNS.
  • Slow first response — the model takes a few seconds to load into memory; subsequent requests are fast.
  • Out of memory — model too large for your VRAM/RAM. Pull a smaller variant or quantization.
  • llama.cpp's responses look weird — wrong chat template for that model. Pass --chat-template matching the family (llama3, qwen, mistral).
  • Empty model list from /v1/models — Ollama needs at least one pulled model. ollama pull llama3.2:3b.

Variations

  • vLLM — for production-style serving (continuous batching, multi-user) on Nvidia GPUs. Different audience but same Tailscale recipe: vllm serve meta-llama/Meta-Llama-3.1-8B-Instruct --port 8000 then tailscale serve --bg http://localhost:8000.
  • Editor integrations — Continue, Aider, Cursor all accept custom OpenAI-compatible base URLs. Point them at your tailnet hostname; you're done.

Where this leads

You have a private API. That's plenty if you're driving it from scripts, editor extensions, or your own code. But chatting with it via curl is awkward — most readers want a real UI for browsing past conversations, switching models mid-thread, and just talking to the thing.
