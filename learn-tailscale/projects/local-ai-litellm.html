🔀 Local AI: multi-user with LiteLLM

Add a proxy in front of your engine that gives you per-user virtual keys, model routing, and transparent cloud fallback. Share your private AI with friends without giving them tailnet access; still chat normally yourself; gracefully fall back to OpenAI/Anthropic when local is down or too slow.

Featured AI/ML Advanced ~30 min Prereqs: parts 1 + 2

Why this project

Parts 1 and 2 left you with a private API and a chat UI on your tailnet. That's everything most readers need. But three real situations push you past it:

  • Sharing with friends — you want a friend to be able to use your AI without you inviting them to your tailnet (which gives them more access than you might want)
  • Cloud fallback — when your local rig is offline, slow, or just outclassed for a hard prompt, you want the same URL to seamlessly route to OpenAI/Anthropic with a frontier model
  • Multi-engine routing — you might run Ollama on one machine for chat and vLLM on another for code, and you want clients to use one stable hostname for both

LiteLLM is an OpenAI-compatible proxy that solves all three: it sits between clients and engines, mints per-user virtual keys, routes model names to wherever you want, and falls back automatically when a backend is down.

Who this helps

  • You want to share API access with friends without inviting them to your tailnet
  • You want a single endpoint that mixes local + cloud models behind virtual keys
  • You want usage tracking and per-user budgets
  • You're running multiple engines on multiple machines and want one stable URL

What you get

  • LiteLLM proxy running in Docker, fronting your engine + any cloud APIs you configure
  • Per-user virtual keys with rate limits and budgets
  • Model routing: clients ask for "smart", you decide what that maps to today
  • Transparent cloud fallback when local is offline
  • Open WebUI re-pointed at LiteLLM, so the chat UI also benefits from routing and fallback

Prerequisites

  • Local AI gateway (part 1) — engine running
  • Local AI: chat UI (part 2) — Open WebUI running, currently the front of Tailscale Serve
  • Optional: an OpenAI or Anthropic API key if you want cloud fallback

Mental model

Final architecture: every client (browser via Open WebUI, or API tools like Continue/Aider/Cursor) talks to LiteLLM. LiteLLM dispatches to your engine for most prompts, falls back to cloud for the rest, and enforces per-user keys on the way in.

Steps

Six steps. Configure LiteLLM, run it in Docker, mint your first key, re-point Tailscale Serve to LiteLLM, re-point Open WebUI through LiteLLM, then verify cloud fallback by killing the local engine.

Configure LiteLLM ~10 min

LiteLLM is config-driven. Save as ~/litellm/config.yaml:

model_list:
  - model_name: llama-3.1-8b
    litellm_params:
      model: ollama/llama3.1:8b
      api_base: http://host.docker.internal:11434

  - model_name: smart           # alias — clients ask for "smart"
    litellm_params:
      model: ollama/qwen2.5:14b
      api_base: http://host.docker.internal:11434

  - model_name: smart           # fallback to cloud if local fails
    litellm_params:
      model: claude-3-5-sonnet-20241022
      api_key: os.environ/ANTHROPIC_API_KEY

litellm_settings:
  num_retries: 2
  request_timeout: 60

general_settings:
  master_key: sk-master-key-rotate-this   # for minting virtual keys
  database_url: "sqlite:///litellm.db"

Two entries with the same model_name set up automatic fallback in declaration order. Clients ask for "smart"; LiteLLM tries Ollama first, falls back to Claude if it errors or times out.

Run LiteLLM in Docker ~5 min

Same container-to-host pattern as Open WebUI in part 2:

docker run -d \
  -p 4000:4000 \
  -v ~/litellm/config.yaml:/app/config.yaml \
  -e ANTHROPIC_API_KEY=sk-ant-... \
  --name litellm \
  --restart always \
  ghcr.io/berriai/litellm:main-stable \
  --config /app/config.yaml
docker run -d \
  -p 4000:4000 \
  --add-host host.docker.internal:host-gateway \
  -v ~/litellm/config.yaml:/app/config.yaml \
  -e ANTHROPIC_API_KEY=sk-ant-... \
  --name litellm \
  --restart always \
  ghcr.io/berriai/litellm:main-stable \
  --config /app/config.yaml

Verify the proxy is up:

curl http://localhost:4000/v1/models -H "Authorization: Bearer sk-master-key-rotate-this"

Mint your first virtual key ~3 min

Virtual keys are how you grant access without sharing the master key. Each one can have its own model whitelist, rate limit, and budget. Use the master key to mint:

curl -X POST http://localhost:4000/key/generate \
  -H "Authorization: Bearer sk-master-key-rotate-this" \
  -H "Content-Type: application/json" \
  -d '{"models": ["llama-3.1-8b", "smart"], "max_budget": 10}'

# Returns: { "key": "sk-...", ... }

Save the returned key. Hand it to a friend, or use it yourself for editor tools so you can rotate it independently of the master key.

Re-point Tailscale Serve at LiteLLM ~2 min

Part 2 left Tailscale Serve pointing at Open WebUI on port 3000. Now we want LiteLLM (port 4000) to be the public-facing service, with Open WebUI being one of LiteLLM's internal clients.

sudo tailscale serve reset
sudo tailscale serve --bg http://localhost:4000
sudo tailscale serve status

What just changed. https://ai-rig.tail-abc.ts.net now lands at LiteLLM. The chat UI URL has effectively moved (we'll fix that next). API clients with virtual keys can now hit your tailnet hostname directly.

Re-point Open WebUI at LiteLLM ~5 min

Open WebUI is currently configured to talk to the engine. Re-point it at LiteLLM so the chat UI inherits all the routing + fallback benefits and uses a virtual key for usage tracking.

In Open WebUI: Admin Panel → Settings → Connections. Update or add an OpenAI-compatible connection:

  • Base URL: http://host.docker.internal:4000/v1 (or http://localhost:4000/v1 on Linux with --network=host)
  • API key: the virtual key from step 3 (or the master key if you want admin-level access)

Save. The model picker now shows everything LiteLLM exposes — your local models and any cloud fallbacks.

If you want chat itself reachable on the tailnet again (alongside the API), add a second Tailscale Serve mounting Open WebUI at a path like /chat:

sudo tailscale serve --bg --set-path=/chat http://localhost:3000

Now https://ai-rig.tail-abc.ts.net/v1/... hits the API; https://ai-rig.tail-abc.ts.net/chat hits the UI.

Verify the cloud fallback ~3 min

Make sure LiteLLM actually falls back when the local engine is unavailable:

# Stop Ollama (or llama.cpp):
sudo systemctl stop ollama       # Linux
# or quit the macOS app

# Now ask LiteLLM for the "smart" model:
curl https://ai-rig.tail-abc.ts.net/v1/chat/completions \
  -H "Authorization: Bearer sk-virtual-key-from-step-3" \
  -H "Content-Type: application/json" \
  -d '{"model":"smart","messages":[{"role":"user","content":"hi"}]}'

# Should still get a response — this time from Claude, not Ollama.
# Check LiteLLM's logs to confirm the fallback fired:
docker logs litellm --tail=20

Restart your engine when you're done testing.

Verify

  • curl /v1/models with a virtual key returns the LiteLLM-exposed model list (local + cloud)
  • Open WebUI's model picker shows the same combined list
  • Killing the local engine and asking for the "smart" alias still returns a response (cloud fallback fired)
  • docker logs litellm shows per-request routing decisions and which key was used

Common issues

  • "Authentication Error" — wrong key, or key was minted with a model whitelist that excludes the model name you asked for. Try with the master key first to isolate.
  • Fallback doesn't fire — check that num_retries is set and that the secondary model entry has working credentials. docker logs litellm will tell you.
  • Open WebUI model picker still shows old engine list — refresh, or remove the old connection in Open WebUI's Admin → Connections.

Variations

  • Editor tool integration — Continue, Aider, Cursor all accept custom OpenAI-compatible base URLs. Point them at https://ai-rig.tail-abc.ts.net/v1 with a virtual key. Free, private code completion that uses your home rig for the cheap stuff and falls back to a cloud frontier model when needed.
  • Multi-rig setup — different engines on different machines (a Mac mini for embeddings, a GPU box for big models). Add multiple api_base entries in LiteLLM's config; route by model name.
  • Caddy minimal-auth alternative — if you only need a single shared API key (no rotation, no per-user limits), Caddy with a header check is simpler than LiteLLM. Less flexible but fewer moving parts.

Caveats

  • Local models lag frontier models on hard reasoning. The 80/20 case is well-served; the 20% isn't. LiteLLM's cloud fallback handles this gracefully.
  • LiteLLM's master key has full access — rotate it, treat it like a database password, never put it in a public repo.
  • Open WebUI and LiteLLM both have admin UIs. Set strong admin passwords; tailnet-only is good but defense-in-depth matters.
  • Claude Code itself doesn't go through LiteLLM — it talks to Anthropic directly. The pattern in this project is for Claude-Code-adjacent tools (Continue/Aider/Cursor), not Claude Code itself.
