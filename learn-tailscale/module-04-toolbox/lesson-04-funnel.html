Tailscale Funnel

Same as Serve, but the door is open to the entire internet. Powerful, and the easiest place to make a security mistake. Read all of this before turning it on.

1What it does

Funnel exposes a service via Tailscale's edge to the public internet at https://your-device.tail-abc.ts.net. Anyone with the URL can hit it. Tailscale provides the cert and the entry point; your device serves the actual content.

This is publishing to the open internet. No auth on Funnel itself — you have to add auth in your application. Don't Funnel something assuming "no one will know the URL"; the certificate transparency logs make all .ts.net hostnames discoverable.

2Decide first: should this be Funnel'd?

Before turning it on, run through this:

  • Does the service already enforce its own auth? (login page, API key, basic auth, OAuth) If no — don't Funnel it.
  • Is the audience public? If only your friends/family need it, use Serve + invite them to your tailnet instead.
  • Does it need rate-limiting / abuse protection? Funnel does some, but if you're getting hammered, you'll want a CDN in front.

The "Is it safe to expose?" tool walks the decision tree with you.

3Enabling it

Funnel is opt-in twice — once at the tailnet level, once per service.

  1. Admin console → Access controls → ensure your policy includes a nodeAttrs block enabling funnel for your devices: 
    "nodeAttrs": [
  { "target": ["autogroup:member"], "attr": ["funnel"] }
]
  2. On the device, run: 
    sudo tailscale funnel --bg 8080
    (Same syntax as Serve, but published publicly.)

4Common safe uses

  • A webhook receiver (GitHub, Stripe, etc.) — the senders authenticate via signed payloads
  • A static demo of a project for a job interview, expiring in a few days
  • A self-hosted public site where you've added auth in the app (Vaultwarden's web vault, for instance)

5Common unsafe uses (don't)

  • Your home assistant dashboard, with no extra auth
  • Your raw SSH or Jellyfin or Plex web UI without checking what they do for unauthenticated requests
  • A dev server you forgot has debug routes enabled

6Turning it off

sudo tailscale funnel --https=443 off

Or revoke at the policy level by removing the funnel attribute from nodeAttrs. The latter is the kill switch.

Three quick questions

Q1.What's the difference between Serve and Funnel?
Right. The audience is the only difference. Same syntax, different reach.
Speed comparable. Audience is the difference.

Q2.You want to expose your Home Assistant dashboard to your phone when you're outside the tailnet. Which is right?
Right. Your phone is on your tailnet → it can already reach Home Assistant directly. No Funnel needed. Funnel would expose Home Assistant to the world for no benefit.
Don't Funnel sensitive admin tools when private access works.
Old approach. Tailscale removes the need.
Not needed for tailnet-only access.
Q3.What's a legitimate Funnel use?
Right. Webhook receivers are a perfect fit — the senders (GitHub) authenticate via signed payloads, so your endpoint is safe to expose publicly.
Plex has auth, but historically has had bugs in pre-auth flows. Better to keep it private.
Dev servers often expose debug endpoints. Don't Funnel.
SSH brute-force attacks are constant. Don't Funnel SSH.
