Server State is Different

Fetching data in a useEffect is the most common beginner pattern, and it's almost always wrong. Server state has different rules — and there's a specific tool for it.

⏱ 25 min 🎯 Tool for the job 🛠 TanStack Query

Why server state is different from UI state

Local UI state (is the menu open, what did the user type, is this checkbox checked) is owned by your component — you're the source of truth.

Server state (a list of datasets, the current user, a row's details) is owned by the server — you're holding a cached copy. That copy can go stale. It can fail to load. It can be out of date across tabs. Multiple components may want the same data at the same time.

None of that is what useState + useEffect is designed for.

The "naive" data fetch — what most tutorials still teach

function Datasets() {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch("/api/datasets")
      .then(r => r.json())
      .then(setData)
      .catch(setError)
      .finally(() => setLoading(false));
  }, []);

  if (loading) return <Spinner />;
  if (error) return <Error />;
  return <List items={data} />;
}

What's broken here — and it's a lot:

  • No caching — if another component mounts and wants the same data, it re-fetches
  • No deduplication — if two components fetch on the same tick, you get two requests
  • No background refetch when the user returns to the tab
  • Race conditions when props change faster than fetches resolve
  • Can't share the "current list" between components without lifting to a store and reimplementing the cache
  • No retry on failure
  • StrictMode causes effects to run twice in dev — your fetch fires twice

TanStack Query — the right tool

TanStack Query (formerly React Query) is a cache + fetcher + state machine for server data. Think of it as React-flavored HTTP with automatic caching, deduplication, background refetch, retries, and request invalidation.

Same component, with TanStack Query

function Datasets() {
  const { data, isPending, error } = useQuery({
    queryKey: ["datasets"],
    queryFn: () => fetch("/api/datasets").then(r => r.json()),
  });

  if (isPending) return <Spinner />;
  if (error) return <Error />;
  return <List items={data} />;
}

This version handles caching, deduplication, stale-while-revalidate, retries, refetch-on-focus, StrictMode safety, and request cancellation on unmount. All of it. You wrote zero of it.

What you get for free

Cache

Keyed by queryKey. Ten components can call useQuery(\{queryKey: ["datasets"]\}) and fire one request. All ten get the same data.

Stale-while-revalidate

When cached data is considered stale (configurable), the next access shows the cached copy immediately AND triggers a background refetch. The UI never blanks out.

Refetch on focus

User switches tabs, comes back — data refreshes automatically. Nothing for you to do.

Retries with backoff

Failed requests retry with exponential backoff by default. Network blip? User never sees it.

Mutations + invalidation

useMutation for writes. Invalidate related queries by key and the cache refetches. Your list updates after a POST automatically.

Request cancellation

Component unmounts mid-fetch? Request cancels via AbortSignal. No memory leaks, no stale state.

The mental model: queries are cached answers

A query is "the cached answer to a question." Its queryKey is the question:

// "all datasets"
useQuery({ queryKey: ["datasets"], queryFn: listDatasets });

// "one dataset by id"
useQuery({ queryKey: ["dataset", id], queryFn: () => getDataset(id) });

// "filtered datasets"
useQuery({ queryKey: ["datasets", { search, tag }], queryFn: () => listDatasets({ search, tag }) });

Different keys = different cached entries. Same key in ten components = shared cache entry. The key is the identity of the data.

Writing with useMutation

function useDeleteDataset() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (id: string) => fetch(`/api/datasets/${id}`, { method: "DELETE" }),
    onSuccess: () => {
      // invalidate the list — it will refetch next time it's accessed
      queryClient.invalidateQueries({ queryKey: ["datasets"] });
    },
  });
}

function DeleteButton({ id }) {
  const { mutate, isPending } = useDeleteDataset();
  return (
    <button onClick={() => mutate(id)} disabled={isPending}>
      {isPending ? "Deleting..." : "Delete"}
    </button>
  );
}

Invalidation is the superpower. You don't update state in a dozen places after a write — you invalidate the cache key for the data that's now stale, and every component using it refetches next time it's in view.

Setting it up (quick reference)

// install
// npm install @tanstack/react-query

// App root
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60_000,         // data considered fresh for 60s
      retry: 2,                   // retry failed requests twice
      refetchOnWindowFocus: true, // refetch when user tabs back in
    },
  },
});

function App() {
  return (
    <QueryClientProvider client={queryClient}>
      <Dashboard />
    </QueryClientProvider>
  );
}

Add the DevTools (they're worth it):

import { ReactQueryDevtools } from "@tanstack/react-query-devtools";

When to use useState vs Zustand vs TanStack Query

State typeExampleTool
Local UIIs this dropdown open? What's in the input?useState
Global UISidebar open, selected filters, multi-step form progressZustand
Server dataList of datasets, current user, a dataset's rowsTanStack Query
DerivedTotal from a list of itemsJust compute it
Form valuesComplex form, validation, async submissionreact-hook-form
URL stateCurrent page, filters in the URLRouter search params (e.g. TanStack Router)

Notice that "one big blob of state" is never the answer. Each kind of state has a different lifecycle and the right tool matches that.

Hot take that's actually correct

Once you put TanStack Query in a project, the amount of "state management" code you write drops by ~60%. Most of what people were trying to do with Redux or useEffect soup was really just server-state handling that's now a library's job.
