The React Rendering Mental Model

If you've been writing React without knowing exactly when components re-render, you've been programming with a fog. This lesson burns the fog off.

⏱ 25 min 🎯 Mental model 🛠 Live React

The two-sentence mental model

React re-runs a component function when its state or its props change. That's it. "Render" in React means "run the component function, compute new JSX, diff against the previous JSX, update the DOM minimally."

Everything confusing about React comes from not having this model clear. Let's anchor it with a live example.

Live — renders are visible

Click the button. Watch the render count increase. Watch the child component flash when it renders. Every time the parent renders, the child re-renders too — even though the child's props haven't changed. This is React's default behavior and it surprises almost everyone.

function Parent() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(count + 1)}>{count}</button>
      <Child />   {/* re-renders every time, even though it has no props */}
    </>
  );
}

Rule: when a parent renders, ALL its children render

Even if their props didn't change. Even if they take no props. This is intentional — React trades "unnecessary" re-renders for simplicity and speed. Re-running functions is cheap; reconciling DOM changes is where the cost actually lives, and React handles that optimally regardless.

Self-taught trap: people think "I'll useMemo everything and React.memo every child for performance." Don't. Most of the time it's the same speed or slower. Optimize when you measure a problem.

When do I actually need to stop a child re-rendering?

Three cases:

  1. The child is expensive to render — a chart with 10k data points, a large list without virtualization
  2. The child has its own expensive side effects tied to rendering (rare, a red flag on its own)
  3. You're chasing a measured performance problem with React DevTools Profiler open

If none of those apply, your child re-rendering is fine. React is fast.

When you DO need it: `React.memo`

React.memo wraps a component so it only re-renders when its props actually change (shallow comparison).

const ExpensiveChart = React.memo(function ExpensiveChart({ data }) {
  // expensive render logic...
  return <svg>{/* ... */}</svg>;
});

But — and this is where people trip — React.memo only helps if the props you pass are referentially stable. If you pass a new object or function every render, memoization is defeated.

Live — broken memoization

The "ExpensiveChart" below is wrapped in React.memo. But the parent passes data=\{[1,2,3]\} — a new array every render. Because [1,2,3] !== [1,2,3] (object identity), memo sees the prop as "changed" every time and re-renders anyway.

Click the button. The chart flashes every time, even though the array content is identical.

// BROKEN: new array every render
const ExpensiveChart = React.memo(({ data }) => { /* ... */ });

function App() {
  return <ExpensiveChart data={[1, 2, 3]} />; // new array each render
}

The fix: stabilize the reference with useMemo, or move the data outside the component entirely.

// FIXED: stable reference
function App() {
  const data = useMemo(() => [1, 2, 3], []);
  return <ExpensiveChart data={data} />;
}

This is why "just add useMemo" doesn't help

Memoizing the child without stable props is pointless — you pay the cost of the memo check AND still re-render. If you reach for React.memo, you must also audit every prop for referential stability. The whole chain matters.

Practically: React.memo is almost always the wrong first move. Fix the component structure first (move expensive stuff down, split state, colocate).

What actually triggers a render?

Exactly three things:

  1. State changes — a useState setter is called with a new value (new by identity)
  2. Props change — the parent passes different props (which means the parent re-rendered)
  3. Context changes — a Context provider higher up passes a new value

That's the whole list. useEffect does not trigger a render — it runs after a render. Mutating a ref does not trigger a render. Mutating an object in state does not trigger a render (this is a bug — use setState(newObject)).

The identity rule

React decides "did state change" by comparing the new value to the old with Object.is. So:

  • setCount(5) after setCount(5) → no render (same value)
  • setItems(items) (same array) → no render
  • setItems([...items]) (new array, same contents) → render
  • setItems(items.push(x)) → no render AND your state is now broken (mutation)

Always create a new object/array when updating state with objects/arrays. This is the single most common bug when people come from OOP backgrounds.

Derived state is not state

Here's a pattern I want to burn into your brain before we go further. Many "renders I can't explain" come from treating derived values as state.

// ❌ BAD — fullName is derived state kept in state
function Profile({ first, last }) {
  const [fullName, setFullName] = useState(first + " " + last);

  useEffect(() => {
    setFullName(first + " " + last);
  }, [first, last]);

  return <h1>{fullName}</h1>;
}

// ✅ GOOD — fullName is computed every render (cheap, always correct)
function Profile({ first, last }) {
  const fullName = first + " " + last;
  return <h1>{fullName}</h1>;
}

The bad version causes an extra render every time first or last changes. The good version is simpler, faster, and always correct. If a value can be computed from props or other state, just compute it.

We'll go deeper into this in Lesson 2 (the "useEffect is not a lifecycle" lesson). For now: if you can derive it, don't store it.

Render count cheatsheet

ActionDoes it re-render?
Call a useState setter with a NEW valueYes
Call a useState setter with the SAME value (Object.is)No (React bails out)
Parent re-rendersYes (children always follow)
Context value changesYes (all consumers re-render)
Mutate a ref (ref.current = x)No
Mutate an object in state (state.x = 5)No (and it's a bug)
Run a useEffectNo (effects run AFTER render, they don't cause one)
Call setState(x) where x === current stateNo — except for objects/arrays where you pass a new reference of the same shape

Self-check

Can you explain why this component renders twice on mount?

function Widget() {
  const [items, setItems] = useState([]);
  useEffect(() => {
    setItems([1, 2, 3]);
  }, []);
  return <div>{items.length} items</div>;
}

Answer: first render with items = [], then the effect runs, calls setItems([1, 2, 3]) (new array), which triggers a second render. If the initial data was available synchronously, you'd skip this by doing useState([1, 2, 3]) or useState(() => computeInitial()). The useEffect is buying you an extra render for no reason — and this is a setup for the kind of bug Lesson 2 fixes.
