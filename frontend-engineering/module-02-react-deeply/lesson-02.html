Hooks You Thought You Knew

The single biggest upgrade for a self-taught React dev is realizing that most of your useEffects are wrong. This lesson fixes that, then goes through the other hooks you use daily and shows what most tutorials got wrong about them.

⏱ 35 min 🎯 Fix anti-patterns ⚠️ Uncomfortable truths

useEffect is not a lifecycle hook

If you learned React from tutorials written 2019–2021, you were probably told that useEffect is the functional-component replacement for componentDidMount / componentDidUpdate / componentWillUnmount. That framing is actively harmful.

The accurate framing, from the React team itself: useEffect is an escape hatch for synchronizing with external systems. External means outside React — the DOM, a websocket, a subscription, a browser API. Most of what your effects probably do is not that.

The self-taught trap

If your component does any of the following in a useEffect, it's probably wrong:

  • Deriving state from props or other state (compute it inline — always)
  • Calling setState based on prop changes (derive, don't sync)
  • Running logic "in response to a user event" (put it in the event handler)
  • Fetching data (use TanStack Query, covered Lesson 4 — never fetch in useEffect directly in production)

The "Effect Gym" guide on react.dev is required reading. Their rule: if you can't name the external system you're synchronizing with, you probably don't need an effect.

The "derive, don't sync" pattern

Bad — useEffect used to derive

function Cart({ items }) {
  const [total, setTotal] = useState(0);

  useEffect(() => {
    setTotal(items.reduce((sum, i) => sum + i.price, 0));
  }, [items]);

  return <div>Total: ${total}</div>;
}

This causes an extra render, can go stale, and is just complicated.

Good — compute during render

function Cart({ items }) {
  const total = items.reduce((sum, i) => sum + i.price, 0);
  return <div>Total: ${total}</div>;
}

One render. Always correct. No effect needed. If the reduce is genuinely expensive (big array, complex calc), wrap it in useMemo. Most of the time it isn't.

The "event handler, not effect" pattern

Bad — syncing based on a state change

function Form() {
  const [submitted, setSubmitted] = useState(false);

  useEffect(() => {
    if (submitted) {
      showToast("Saved!");
      navigate("/dashboard");
    }
  }, [submitted]);

  return <button onClick={() => setSubmitted(true)}>Save</button>;
}

Why is this wrong? Because those things happen in response to a click, not in response to state changing. The state change is an intermediate artifact.

Good — do the work in the handler

function Form() {
  function handleSubmit() {
    showToast("Saved!");
    navigate("/dashboard");
  }
  return <button onClick={handleSubmit}>Save</button>;
}

The logic lives where the trigger lives. Easier to read, easier to debug, no "why did my effect fire three times" mystery.

When IS useEffect appropriate?

  • Attaching a listener to window, document, or the DOM (and detaching on unmount)
  • Opening a WebSocket / subscription (and closing on unmount)
  • Manually interacting with a third-party library's imperative API that isn't React-aware
  • Syncing with localStorage (though even this is often better via event handlers)

Notice the pattern: the target is always outside React's world. If the target is React state, props, or other components, you're using the wrong tool.

Live example — a legit useEffect

This one is a good useEffect: it attaches a window resize listener, which lives outside React's model.

function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);
  useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);
  return width;
}

This is the shape of a good effect: subscribe, return a cleanup that unsubscribes. You're integrating with an external system.

useState pitfalls

Functional updates when state depends on previous state

// ❌ can go stale in async contexts
const increment = () => setCount(count + 1);

// ✅ always correct
const increment = () => setCount(c => c + 1);

Why? If increment is called multiple times before React re-renders, the first version closes over a stale count and all the increments compute from the same base. The functional form reads the actual current value.

Lazy initial state for expensive setup

// ❌ calls computeExpensive() on every render (though only uses the first result)
const [state, setState] = useState(computeExpensive());

// ✅ calls it once
const [state, setState] = useState(() => computeExpensive());

Pass a function, not a value. React calls it once on mount.

useRef — the non-rendering slot

A ref holds a mutable value that persists across renders but does NOT trigger a re-render when you change it. Two main uses:

  1. DOM access — <input ref={inputRef} />, then inputRef.current.focus()
  2. Storing values that shouldn't cause renders — timeouts, previous values, counts of renders, anything where "the component needs to remember this but doesn't need to redraw"

Decision rule

Does the UI need to show the new value? Use state.

Does the UI NOT need to redraw when this changes? Use a ref.

Live — input focus with useRef

function FocusDemo() {
  const inputRef = useRef(null);
  return (
    <>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current.focus()}>Focus</button>
    </>
  );
}

useMemo and useCallback — the two you overuse

These exist for referential equality — ensuring the same object/function reference comes back across renders. They are NOT for making slow code fast; they are for preserving identity so that memoized children, effect dependency arrays, or context values behave correctly.

When you actually need useMemo

  1. The computation is genuinely expensive (measure with DevTools first)
  2. The result is passed to a React.memo'd child or a useEffect dependency, and you need referential stability

When you actually need useCallback

  1. The function is passed to a React.memo'd child that would otherwise re-render every time
  2. The function is a dependency of another hook

Over-memoization is a real cost

Every useMemo still runs a comparison every render. Every useCallback allocates an array of deps every render. When you sprinkle these everywhere "just in case", you are slowing your component down, not speeding it up. Worse, you're hiding the component structure under noise.

Default to NOT memoizing. Memoize when you've measured a problem or when you need referential stability for correctness.

Speaking of measured problems — open React DevTools and enable "highlight updates when components render." Click around your app. Any component that flashes on every interaction is your first candidate for optimization. Don't optimize what's not flashing.

Custom hooks — your best abstraction tool

A custom hook is just a function that calls other hooks. By convention its name starts with use. That's the entire contract — there's no magic. What makes custom hooks valuable is that they let you name a concept and hide the wiring.

// before: wiring scattered in the component
function Profile() {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetchUser().then(setUser);
  }, []);
  // ...
}

// after: named concept, reusable, testable
function useCurrentUser() {
  const [user, setUser] = useState(null);
  useEffect(() => { fetchUser().then(setUser); }, []);
  return user;
}

function Profile() {
  const user = useCurrentUser();
  // ...
}

Every time you feel the urge to copy-paste a hook combo across two components, turn it into a custom hook. This is 80% of what good React code looks like — composing small custom hooks.

The full hook inventory, opinionated

HookWhen to reach for itGotchas
useStateUI state owned by this componentFunctional updates when updating from prior state
useReducerRelated state that transitions together (multi-step forms, undo/redo)Overkill for single values — don't force it
useEffectSyncing with an external system (subscriptions, DOM, browser APIs)Almost never correct for derived state or event-triggered work
useRefDOM access, non-rendering mutable storageNot a state replacement — no re-render when .current changes
useMemoExpensive computation OR referential stabilityDon't sprinkle — overhead isn't free

useIdStable unique ID for SSR (labels, ARIA)Use it for accessibility wiring, not as a key

useTransitionMarking a state update as non-urgent (concurrent features)Advanced — revisit once you've internalized the basics
useDeferredValueDeferring a re-render for a slow-to-render childSame — advanced

The 80/20

In 80% of components you'll only use useState and a few custom hooks. If a component is full of useEffect and useMemo, it's probably doing too much and needs to be split or refactored. This is a smell worth fixing, not a complexity to live with.
