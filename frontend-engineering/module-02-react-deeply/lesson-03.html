State Architecture — Colocate, Lift, Derive

State is where your React codebase lives or dies. A good decision tree beats any library. Here's the one I use.

⏱ 25 min 🎯 Decision tree 🛠 No magic

The three-question decision tree

  1. Can I derive this value from props or other state? → compute it inline. Not state.
  2. Does exactly one component need this state? → useState inside that component. Done.
  3. Does the state belong to the server? (user data, product list, dataset rows) → TanStack Query. Not useState. Lesson 4.

If you still have state that survives all three questions, then consider lifting, context, or a store. That's the rest of this lesson.

Colocate state — keep it close to where it's used

Beginner instinct: put all state in the top-level component and pass it down. Result: every interaction in any leaf component re-renders the whole tree. The app gets sluggish and tangled.

Better instinct: state lives as deep in the tree as possible, close to the component that actually uses it. Only lift when you genuinely need two siblings to share it.

Over-lifted — avoid

function App() {
  const [searchTerm, setSearchTerm] = useState("");
  const [isMenuOpen, setMenuOpen] = useState(false);
  const [activeTab, setActiveTab] = useState("overview");
  // 40 more useStates...
  return (
    <Layout>
      <Search term={searchTerm} onChange={setSearchTerm} />
      <Menu open={isMenuOpen} onOpenChange={setMenuOpen} />
      <Tabs active={activeTab} onChange={setActiveTab} />
    </Layout>
  );
}

Colocated — better

function App() {
  return (
    <Layout>
      <Search />    {/* owns its own term */}
      <Menu />      {/* owns its own open state */}
      <Tabs />      {/* owns its own active tab */}
    </Layout>
  );
}

function Search() {
  const [term, setTerm] = useState("");
  return <input value={term} onChange={...} />;
}

Now a keystroke in Search only re-renders Search. The menu and tabs don't know or care.

Lifting state — when you actually need to

When two siblings need the same state, lift it to their nearest common ancestor. Not higher. The classic pattern:

function TabsContainer() {
  const [active, setActive] = useState("overview");
  return (
    <>
      <TabsList active={active} onChange={setActive} />
      <TabsPanel active={active} />
    </>
  );
}

Both TabsList and TabsPanel need active. Their common parent holds it. If only one needed it, it would live inside that one.

The smell to watch for

If you're passing state down through 3+ layers of components that don't use it (prop drilling), either:

  • Split your component tree differently — the intermediate components are probably doing too much
  • Use Context for dependency injection (next section)
  • Use a state store (two sections down)

Context — for dependency injection, not state management

Context is React's tool for passing values deep without prop drilling. It is not a state management solution — it's the wire that carries state (or anything else) across the tree.

What Context is good for

  • Theme (current colors, mode)
  • Current user / auth state
  • Internationalization / locale
  • Configuration that rarely changes
  • Feature flags

What Context is bad for

  • State that changes frequently (every consumer re-renders when the context value changes)
  • Large shared state (form values, a list of items, filters) — use a store instead

If you put your whole app state in a single Context, the entire app re-renders on every state change. People learn this the hard way. Context works best when the value is stable or rarely changes.

// Pattern: one context for static-ish config per concern
const ThemeContext = createContext();

function ThemeProvider({ children }) {
  const [theme, setTheme] = useState("dark");
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

// always wrap consumers with a typed hook
function useTheme() {
  const v = useContext(ThemeContext);
  if (!v) throw new Error("useTheme must be used inside ThemeProvider");
  return v;
}

Don't wrap value in useMemo blindly

You'll see "always useMemo the context value" advice. That only matters when the value is an object assembled on every render. If the value IS just a piece of state (like [theme, setTheme]), and theme is a primitive, React.memo on consumers + identity-stable setter already handle it.

Stores — for real global state

When you have application-wide state that many components read and write — filters on a dashboard, a shopping cart, a multi-step form, UI state like "is the side panel collapsed" — you want a store.

The modern default is Zustand. It's small (~1KB), has no provider boilerplate, and uses useSyncExternalStore under the hood so consumers only re-render when the slice they selected actually changes.

// store.ts
import { create } from "zustand";

type DashboardStore = {
  selectedDatasetId: string | null;
  sidebarOpen: boolean;
  setSelectedDataset: (id: string | null) => void;
  toggleSidebar: () => void;
};

export const useDashboard = create<DashboardStore>((set) => ({
  selectedDatasetId: null,
  sidebarOpen: true,
  setSelectedDataset: (id) => set({ selectedDatasetId: id }),
  toggleSidebar: () => set((s) => ({ sidebarOpen: !s.sidebarOpen })),
}));

Consume in any component:

function SidebarToggle() {
  // select only what you need — this component only re-renders when sidebarOpen changes
  const sidebarOpen = useDashboard((s) => s.sidebarOpen);
  const toggle = useDashboard((s) => s.toggleSidebar);
  return <button onClick={toggle}>{sidebarOpen ? "⟨" : "⟩"}</button>;
}

No provider. No wrapping your app. Just import and use. This is what "modern React state management" feels like — it should be boring.

What about Redux?

Redux Toolkit is fine — it's essentially Zustand with extra structure (slices, RTK Query, dev tools). Large teams with lots of shared state conventions sometimes pick it. For new projects under ~50 engineers: Zustand. For greenfield on the analytics dashboard we're building: Zustand.

const total = items.reduce((s, i) => s + i.price, 0);

Single component owns it. This should be 60–80% of your state.

Lift to nearest common ancestor

Context for dependency injection

Theme, current user, config. Stable values, rarely changes.

Zustand store

Filters, UI state, carts, multi-step forms. Only the slices you select re-render.

if it's server data

TanStack Query (Lesson 4)

Lists from an API, user details, dataset rows. Never put this in useState.

The rule that matters

Server state is fundamentally different from UI state. Lesson 4 is about that. Until then, the takeaways:

  1. Derive before you store. Compute is cheap.
  2. Keep state deep in the tree. Lift only when forced.
  3. Context for values that rarely change (theme, user). Not for fast-moving state.
  4. Zustand for actual global state. Not Redux-by-default, not Context-by-default.
