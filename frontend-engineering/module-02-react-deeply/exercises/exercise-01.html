Rendering Detective

Six real React components with real bugs. Read each one, decide what's wrong and how to fix it, then reveal the answer. Treat it like a code review — if you can't articulate the bug in one sentence, you haven't really seen it yet.

Ground rules

Don't peek at the answer until you've written (or at least mentally composed) a diagnosis. Self-check beats skim-reading ten times over.

Case 1: the chart that re-renders on every keystroke

01 · render cascade

A dashboard has a search bar and a chart below it. Every time the user types one character in the search, the chart flashes in DevTools (visibly re-renders). The chart doesn't use the search term. Diagnose and fix.

function Dashboard() {
  const [search, setSearch] = useState("");
  return (
    <>
      <input value={search} onChange={e => setSearch(e.target.value)} />
      <ExpensiveChart data={CHART_DATA} />
    </>
  );
}
Your answer:
Reveal diagnosis

Diagnosis: Every keystroke triggers setSearch, which re-renders Dashboard. React's rule: when a parent renders, children follow — so ExpensiveChart re-renders too, even though its props haven't changed.

Fix: Two options. (a) Wrap ExpensiveChart in React.memo AND ensure CHART_DATA is a stable reference (module-level constant is fine, useMemo if it's computed). (b) Better — restructure so the search input has its own child component that owns the search state. Then typing doesn't re-render Dashboard at all.

// option b
function Dashboard() {
  return (
    <>
      <SearchBar />  {/* owns its own state now */}
      <ExpensiveChart data={CHART_DATA} />
    </>
  );
}

Colocating state is usually the cleaner fix. Reach for React.memo only when restructuring isn't feasible.

Case 2: the memoized child that isn't

02 · broken memo

ExpensiveChart is wrapped in React.memo, but DevTools shows it re-renders every time the parent does. Why?

const ExpensiveChart = React.memo(function ExpensiveChart({ data, onHover }) {
  return <svg>...</svg>;
});

function Dashboard({ items }) {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <ExpensiveChart
        data={items.filter(i => i.active)}
        onHover={(i) => console.log(i)}
      />
    </>
  );
}
Your answer:
Reveal diagnosis

Diagnosis: Two props defeat React.memo:

  • data={items.filter(...)} creates a NEW array every render
  • onHover={(i) => ...} creates a NEW function every render

React.memo does shallow comparison — new references look like changed props, so it re-renders.

Fix: Stabilize both.

function Dashboard({ items }) {
  const [count, setCount] = useState(0);
  const activeItems = useMemo(() => items.filter(i => i.active), [items]);
  const handleHover = useCallback((i) => console.log(i), []);
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <ExpensiveChart data={activeItems} onHover={handleHover} />
    </>
  );
}

Principle: React.memo only works if every prop is referentially stable. If you can't guarantee that, drop the memo.

Case 3: the double-mount fetch

03 · strict mode

A user reports that after clicking "Save" twice, their server logs show four POST requests, not two. The save handler looks fine. Where are the extra requests coming from?

function Profile() {
  useEffect(() => {
    fetch("/api/analytics/page-view", { method: "POST" });
  }, []);
  return <div>Profile</div>;
}
Your answer:
Reveal diagnosis

Diagnosis: React's <StrictMode> (enabled by default in Vite / Next.js dev) intentionally double-invokes effects in development to help you catch missing cleanups. A POST with no guard fires twice.

This isn't a production bug — StrictMode only does this in dev — but it signals that your effect has a side effect that can't safely re-run. That's a real code smell.

Fix: Analytics pings like this don't belong in useEffect in the first place. Fire them when the navigation happens, or use a router-level hook. If you must use useEffect, either add a guard or, better, move the analytics logic into the event that actually triggered the page visit.

Broader principle: effects should be idempotent — running twice should have the same end state as running once. If they aren't, something else should be driving the side effect.

Case 4: the stale click handler

04 · stale closure

A counter with "increment 10 times" button. Clicking once should increment by 10, but it only increments by 1. What gives?

function Counter() {
  const [count, setCount] = useState(0);

  const incrementTen = () => {
    for (let i = 0; i < 10; i++) {
      setCount(count + 1);
    }
  };

  return (
    <>
      <div>{count}</div>
      <button onClick={incrementTen}>+10</button>
    </>
  );
}
Your answer:
Reveal diagnosis

Diagnosis: Inside incrementTen, count is captured at the time the handler was created — it's a stale closure. Calling setCount(0 + 1) ten times in a row just sets count to 1 repeatedly. React batches these and you see a single increment.

Fix: Use the functional updater form — it reads the actual current state each time, not a captured one.

const incrementTen = () => {
  for (let i = 0; i < 10; i++) {
    setCount(c => c + 1);  // ← functional form
  }
};

General rule: any time you update state based on the previous state, use the function form. It's not an optional style choice.

Case 5: the mutation that doesn't render

05 · object mutation

Adding an item to a list. The call runs, no error — but the UI doesn't update. Why?

function TodoList() {
  const [todos, setTodos] = useState([]);

  const addTodo = (text) => {
    todos.push({ id: Date.now(), text });
    setTodos(todos);
  };

  return <div>{todos.map(t => <p key={t.id}>{t.text}</p>)}</div>;
}
Your answer:
Reveal diagnosis

Diagnosis: todos.push(...) mutates the same array. Then setTodos(todos) passes the SAME reference. React compares with Object.is, sees no change, bails out on the render. The array really did get longer — the UI just never got told about it.

Fix: Never mutate state. Create a new array.

const addTodo = (text) => {
  setTodos([...todos, { id: Date.now(), text }]);
  // or with the functional form (safer in async):
  setTodos(prev => [...prev, { id: Date.now(), text }]);
};

General rule: state is immutable from React's perspective. Always construct a new object/array when updating. If your mutations get complicated, use Immer or a reducer.

Case 6: the effect that never stops firing

06 · deps loop

A component where the effect runs over and over — browser console is spamming logs. Find the loop.

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const options = { include: ["profile", "settings"] };

  useEffect(() => {
    fetchUser(userId, options).then(setUser);
  }, [userId, options]);

  return <div>{user?.name}</div>;
}
Your answer:
Reveal diagnosis

Diagnosis: options is a new object every render. The effect's dependency array sees a "new" value, runs the effect, which calls setUser, which triggers a re-render, which creates another new options — infinite loop.

Fix: Either move options outside the component (if it's static), or stabilize it with useMemo, or — most often the right answer — just inline the object in the fetch call and remove it from deps:

useEffect(() => {
  fetchUser(userId, { include: ["profile", "settings"] }).then(setUser);
}, [userId]);

Principle: effect dependency arrays only work with referentially-stable values. Objects, arrays, and functions declared inside the component body are not stable. Either lift them out, memoize them, or don't depend on them.

Better still: don't fetch in useEffect at all (see Lesson 4). useQuery({ queryKey: ["user", userId, { include: ["profile", "settings"] }], queryFn: ... }) handles this correctly — TanStack Query structurally hashes the queryKey so identity doesn't matter.

Pattern recognition

All six cases boil down to three recurring patterns. When you review React code, check for these:

  1. Referential identity problems — new objects/functions/arrays created inline, defeating memoization or causing effect loops
  2. Stale closures — handlers that captured a value when they were defined and still reference the stale version
  3. Mutation when React expects immutability — pushing/splicing/assigning instead of creating new values

If you can spot these in five seconds, your React review skills are on par with most senior front-end engineers.
