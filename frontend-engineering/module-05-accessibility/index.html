Module 5

Accessibility as a First-Class Concern

Accessibility is not a checklist you run at the end. It's a constraint on how you build — and when you do it right, the result is a better product for everyone. This module makes it habitual.

Planned lessons

preview

Semantic HTML — the 80% win

Why <button> beats <div onClick> every time. Headings as document structure. Landmarks (header, nav, main, aside, footer).

ARIA — when to use it, when not to

The first rule of ARIA: don't. The second rule: use native semantics first. When ARIA is the right answer (tabs, dialogs, menus, live regions), and when it's the wrong one.

Focus management

:focus-visible done right, focus outlines you don't hate, roving tabindex for composite widgets, returning focus after modals and drawers.

Keyboard navigation

The keyboard-only audit — can you do every action without a mouse? Arrow key patterns, Escape, skip links, keyboard shortcuts.

Screen reader testing

VoiceOver on macOS (built-in, free), NVDA on Windows. 15 minutes of testing catches 90% of issues. What to listen for.

Contrast, motion, and user preferences

WCAG AA/AAA contrast, prefers-reduced-motion, prefers-color-scheme, prefers-contrast. Respecting what the OS says.

Audit & fix — the dashboard accessibility pass

Run axe DevTools and Lighthouse over your capstone. Fix every issue. Do a keyboard-only walkthrough. Do a VoiceOver walkthrough.

Build an accessible Combobox from scratch

The hardest widget to get right. Listbox, arrow key nav, aria-activedescendant, announcement of filtered results.
