Headless UI — Why Radix Won

"Headless" components give you behavior, state, and accessibility — but no styles. You bring the look; they handle the hard parts. This is now the dominant pattern for high-quality component libraries, and for good reason.

The old trade-off was "use Material UI and fight its styles" vs "roll your own and ship inaccessible garbage". Headless libraries break the trade-off: take the hard parts (focus management, keyboard nav, ARIA, collision detection for popovers, focus trap for dialogs) and skip the styles entirely. You get clean hooks or unstyled primitives and write CSS exactly how you want.

What "the hard parts" actually means

If you think a Dialog is just a centered div with a dark overlay, you haven't shipped one. Here's what a real accessible Dialog has to do:

  • Trap focus inside it while open — Tab cycles within, Shift+Tab wraps
  • Return focus to the trigger element when it closes
  • Close on Escape key
  • Close on backdrop click (optional, configurable)
  • Prevent background scroll while open
  • Hide the rest of the page from assistive tech (aria-hidden on siblings, inert, or a focus guard layer)
  • Portal to the end of the document so it escapes overflow: hidden and stacking-context bugs
  • Announce itself to screen readers (role="dialog", aria-labelledby, aria-describedby, aria-modal="true")
  • Animate in/out and wait for the exit animation before unmounting
  • Nest correctly when one dialog opens another

Every item on that list is something shipped apps get wrong. Radix gets them all right. That's the pitch.

What using Radix looks like

import * as Dialog from "@radix-ui/react-dialog";

function DatasetSettings() {
  return (
    <Dialog.Root>
      <Dialog.Trigger asChild>
        <Button variant="ghost">Settings</Button>
      </Dialog.Trigger>
      <Dialog.Portal>
        <Dialog.Overlay className="dialog-overlay" />
        <Dialog.Content className="dialog-content">
          <Dialog.Title>Dataset settings</Dialog.Title>
          <Dialog.Description>
            Change refresh cadence, retention, and access.
          </Dialog.Description>
          {/* your form */}
          <Dialog.Close asChild>
            <Button variant="ghost">Cancel</Button>
          </Dialog.Close>
        </Dialog.Content>
      </Dialog.Portal>
    </Dialog.Root>
  );
}

Notes on what's happening here:

  • The structure is a compound component (Dialog.Root + subcomponents sharing state). You learned that pattern in Lesson 2.
  • asChild tells Radix not to render its own <button>, but to merge its trigger behavior onto your Button. No extra wrapper div, no aria-* juggling, no ref forwarding you forgot to do.
  • Dialog.Portal renders to document.body, escaping overflow: hidden parents.
  • Styling is entirely yours: the only visual thing Radix gives you is nothing. You write .dialog-overlay and .dialog-content however you like.
  • Accessibility — focus trap, Escape, title/description linkage — all automatic.

The asChild pattern, unpacked

Without asChild, Dialog.Trigger renders its own <button>. You'd end up with:

<Dialog.Trigger>
  <Button variant="ghost">Settings</Button>
</Dialog.Trigger>

// rendered HTML:
<button>  {/* Radix's */}
  <button class="btn-ghost">Settings</button>  {/* yours */}
</button>

A button inside a button — invalid HTML, broken semantics. So Radix gives you asChild:

<Dialog.Trigger asChild>
  <Button variant="ghost">Settings</Button>
</Dialog.Trigger>

// rendered HTML:
<button class="btn-ghost" onClick={...} aria-expanded="..." aria-controls="..." ref={...}>
  Settings
</button>

Behavior merged onto your child. The library stays invisible in the DOM. This is what "headless" really means at the primitive level — you own the markup; the library owns the logic.

Under the hood

asChild uses React.cloneElement to inject props (onClick, ref, aria-*) into the single child. If you pass multiple children or a non-element, it throws. If Radix and your child both define an onClick, both fire — Radix composes them.

shadcn/ui — Radix with styles you own

The most popular React UI kit of 2024–2026 isn't a library at all — shadcn/ui is a CLI that copies pre-styled Radix components into your own repo. You run npx shadcn add dialog and it writes a dialog.tsx file into src/components/ui/ that you can edit like any other file.

Why this won:

  • You own the code. No versioned dependency pinning you in. Need to change a padding? Edit the file.
  • Radix inside — you get all the accessibility and behavior for free.
  • Tailwind classes are plain CSS classes — no CSS-in-JS runtime cost, no styled-components theme gymnastics.
  • Design tokens live in your CSS. Swap the palette by changing custom properties.

For the capstone dashboard, this is probably the right call: npx shadcn init, then add button, dialog, tabs, tooltip, dropdown-menu, toast as you need them.

The headless library landscape

  • Radix UI — the gold standard for React. Primitive-first, asChild pattern, great docs. What shadcn/ui is built on.
  • Ariakit — similar philosophy, sometimes more flexible primitives. Strong state composition.
  • React Aria (Adobe) — the most thorough accessibility work in the ecosystem. Hooks-based (useButton, useDialog) rather than components. Powers Adobe's own apps.
  • Base UI (MUI's new headless line) — MUI team's Radix-style take, in preview.
  • Headless UI (Tailwind Labs) — smaller scope than Radix, simpler API, first-party Tailwind feel. Good for projects that want fewer moving parts.

When NOT to use a headless library

  • Throwaway internal tools where you just need a form and a table. Just use MUI or Ant Design and ship.
  • When you have real design constraints AND bandwidth is tight — a pre-styled kit gets you 80% of the way there faster. You can migrate later.
  • For fully custom, extremely simple elements — a plain <button> with your classes is still better than importing a library for one button.

But for a public-facing product, a design-system-first team, or anything where the visual identity matters — headless is the move.

Takeaways

  1. Headless libraries ship behavior + accessibility without styles.
  2. They win because the hard parts of UI — focus trap, keyboard nav, ARIA, portals — are exactly what shipped apps get wrong.
  3. The asChild / slot pattern lets library logic merge onto your own markup, keeping the DOM clean.
  4. shadcn/ui combines Radix's headless primitives with Tailwind-styled component files you own in your own repo. For most new React apps in 2026, it's the default choice.
  5. You probably shouldn't implement a Dialog from scratch in production. You should implement one once, for your own learning. (Next exercise.)
