Compound Components

A composition pattern where a parent component shares state with related children via context. It's how Tabs, RadioGroup, Accordion, and Select components actually work under the hood.

⏱ 25 min 🎯 The real pattern

The pattern, in one picture

<Tabs defaultValue="overview">
  <Tabs.List>
    <Tabs.Trigger value="overview">Overview</Tabs.Trigger>
    <Tabs.Trigger value="details">Details</Tabs.Trigger>
    <Tabs.Trigger value="settings">Settings</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Panel value="overview">Overview content</Tabs.Panel>
  <Tabs.Panel value="details">Details content</Tabs.Panel>
  <Tabs.Panel value="settings">Settings content</Tabs.Panel>
</Tabs>

The <Tabs> parent owns the selected value. Triggers read it to highlight themselves. Panels read it to decide whether to render. The consumer never wires this — the components share state through React context that only <Tabs> provides.

Build it — ~40 lines

import { createContext, useContext, useState, ReactNode } from "react";

type TabsCtx = { value: string; setValue: (v: string) => void };
const TabsContext = createContext<TabsCtx | null>(null);

function useTabs() {
  const ctx = useContext(TabsContext);
  if (!ctx) throw new Error("Tabs.* must be used inside <Tabs>");
  return ctx;
}

export function Tabs({
  defaultValue,
  children,
}: { defaultValue: string; children: ReactNode }) {
  const [value, setValue] = useState(defaultValue);
  return (
    <TabsContext.Provider value={{ value, setValue }}>
      <div>{children}</div>
    </TabsContext.Provider>
  );
}

Tabs.List = function List({ children }: { children: ReactNode }) {
  return (
    <div role="tablist" className="tabs-list">
      {children}
    </div>
  );
};

Tabs.Trigger = function Trigger({
  value,
  children,
}: { value: string; children: ReactNode }) {
  const { value: active, setValue } = useTabs();
  const isActive = active === value;
  return (
    <button
      role="tab"
      aria-selected={isActive}
      aria-controls={`panel-${value}`}
      id={`tab-${value}`}
      tabIndex={isActive ? 0 : -1}
      onClick={() => setValue(value)}
      className="tab-btn"
    >
      {children}
    </button>
  );
};

Tabs.Panel = function Panel({
  value,
  children,
}: { value: string; children: ReactNode }) {
  const { value: active } = useTabs();
  if (active !== value) return null;
  return (
    <div
      role="tabpanel"
      id={`panel-${value}`}
      aria-labelledby={`tab-${value}`}
      className="tab-panel"
    >
      {children}
    </div>
  );
};

What this demonstrates

  • Shared state via context. The parent owns it; children read it. No prop drilling.
  • Implicit coordination. Consumers write natural-looking JSX; the components figure out which is active.
  • Accessibility is built in. role="tab", aria-selected, aria-controls — the consumer doesn't think about ARIA at all.
  • Error message on misuse. Tabs.Trigger thrown from outside <Tabs> — good DX.

When to reach for this pattern

Whenever a set of child components must cooperate around shared state. Classic examples:

  • Tabs (which tab is active)
  • Accordion (which sections are open)
  • RadioGroup (which option is selected)
  • Select / Dropdown (is it open, which item is highlighted, selected value)
  • Menu (open/closed, active item, keyboard nav)
  • Form (validation state, submit handler)

All of these are significantly better as compound components than as "one monolithic Tabs component with an items array".

Slots — the lower-level primitive

You can go even further: let the consumer replace the element that a part renders as, not just its children. That's the "slot" or "asChild" pattern, pioneered by Radix.

<Tooltip>
  <Tooltip.Trigger asChild>
    <Button variant="ghost">?</Button>
  </Tooltip.Trigger>
  <Tooltip.Content>Extra context goes here</Tooltip.Content>
</Tooltip>

The asChild prop tells Tooltip.Trigger to not render its own <button>, but instead merge its behavior onto the provided child (here, <Button>). This lets the tooltip's aria-wiring, event listeners, and ref forwarding apply to your existing button without wrapping it.

You probably won't implement asChild yourself on day 1 — use Radix or a similar library. But know the pattern exists and what it does. It's how Radix, Ariakit, React Aria, and Base UI all work.

Takeaways

  1. For any "family of related children," reach for compound components with React context as the shared medium.
  2. The parent owns state; children read it via a typed hook (useTabs(), useForm(), etc.).
  3. Accessibility wiring (role, aria-*, keyboard nav) lives in the components, not on the consumer.
  4. Throw a clear error when a child is used outside its parent — great DX, quick debugging.
  5. The next level is asChild/slot composition. That's what Lesson 3 (headless UI) is about.
