Composition Over Configuration

The most important decision you'll make about a component's API: do consumers configure it with props, or compose it with children? The latter scales. The former collapses.

⏱ 20 min 🎯 API design

The two paths a reusable component can take

Imagine you're building a Card component for the dashboard.

Configuration-first API — avoid

<Card
  title="Revenue"
  subtitle="Last 30 days"
  icon={<DollarIcon />}
  actionText="View details"
  actionHref="/revenue"
  badge="NEW"
  showBadge={true}
  footer={<small>Updated 2 min ago</small>}
/>

Looks fine on day 1. On day 30 a designer asks for a card with two actions. Now you're adding secondaryActionText and secondaryActionHref. Day 45: an action with an icon. Day 60: one card has a chart in the body. The prop surface grows to 20+ props, half used once, and the rendering logic becomes a jungle of {showBadge && ...}.

Composition-first API — prefer

<Card>
  <Card.Header>
    <DollarIcon />
    <Card.Title>Revenue</Card.Title>
    <Card.Subtitle>Last 30 days</Card.Subtitle>
    <Badge>NEW</Badge>
  </Card.Header>
  <Card.Body>
    <LineChart data={data} />
  </Card.Body>
  <Card.Footer>
    <Link href="/revenue">View details</Link>
    <small>Updated 2 min ago</small>
  </Card.Footer>
</Card>

The consumer composes exactly what they need. New design requirements? Just write more composition — no new props on Card.

Why composition wins

  1. Prop surface stays small. Card has two props: className and children. Forever.
  2. Consumer flexibility is unlimited. Two actions? Compose two. Custom footer? Write one. Need a badge AND a warning icon? Both go in the header.
  3. Layouts emerge from the markup, not conditional logic. Reading the JSX tells you exactly what renders. No mental simulation of {showX && a} {showY && b}.
  4. Semantics are preserved. The tree looks like the visual hierarchy.

The children prop is your best friend

Most React components should accept children. If you find yourself taking a content or body prop, you're probably doing it wrong — children is already that, and it's idiomatic.

// ❌
<Panel content={<ThingINeedToRender />} />

// ✅
<Panel><ThingINeedToRender /></Panel>

Prefer children. Prefer composition. If a prop accepts a JSX element, ask yourself: could this be a named slot inside the component instead?

When configuration IS appropriate

Composition isn't a zero-sum replacement for props. Use configuration (props) for things that are about the component's behavior or appearance, not its contents.

  • variant="primary" | "secondary" | "ghost" — picks a style preset
  • size="sm" | "md" | "lg" — sizing
  • disabled, loading — state flags
  • onClick, onSubmit — event handlers

Use composition (children / slots) for things that ARE the content:

  • Labels, titles, descriptions
  • Icons
  • Actions (buttons inside a dialog footer)
  • Nested subcomponents

The test question

When a prop takes a JSX element or a string meant to be displayed, ask: "Could this be children or a named slot?" If yes, make it one.

"But I want to enforce a structure"

Sometimes you want to say "this Card MUST have a header and a body, and the header goes on top." Composition doesn't lose that — you just enforce it inside the component via convention + TypeScript.

function Card({ children, className }: { children: ReactNode; className?: string }) {
  return <div className={cn("card", className)}>{children}</div>;
}

Card.Header = function CardHeader({ children }: { children: ReactNode }) {
  return <div className="card-header">{children}</div>;
};

Card.Body = function CardBody({ children }: { children: ReactNode }) {
  return <div className="card-body">{children}</div>;
};

Card.Footer = function CardFooter({ children }: { children: ReactNode }) {
  return <div className="card-footer">{children}</div>;
};

Three tiny subcomponents. The consumer uses Card.Header / Card.Body / Card.Footer and gets autocomplete. The parent applies the outer layout; each child applies its own internal styling. If the consumer puts them in a weird order, that's their call — the component doesn't force it.

This "dot-notation subcomponent" pattern is used everywhere — by Radix, by Material UI, by Tailwind UI, by any serious component library. We'll build our own in Lesson 2 (compound components).

The dashboard Card you'll actually use

Preview of what you'll build in Exercise 1 (next module's capstone tie-in):

<Card>
  <Card.Header>
    <Card.Title>Weekly signups</Card.Title>
    <Card.Actions>
      <IconButton icon="refresh" onClick={refetch} />
      <IconButton icon="more" onClick={openMenu} />
    </Card.Actions>
  </Card.Header>
  <Card.Body>
    <LineChart data={data} />
  </Card.Body>
</Card>

Five subcomponents. Any card pattern in your dashboard expressible in this vocabulary. No showHeader prop, no primaryActionLabel, no 20-prop config nightmare.
