Module 1 · Lesson 4

Modern CSS

CSS from 2022 onwards is a different language. Custom properties, container queries, :has(), OKLCH color. Four features that kill a pile of old workarounds.

⏱ 20 min 🎯 No polyfills needed 🛠 Theming playground

#1 — CSS Custom Properties (variables)

CSS has real variables now. Define them on any selector, read them anywhere inside that element's subtree. They cascade and inherit just like any other CSS property, which is what makes them the foundation of every modern theming system.

:root {
  --color-bg:     oklch(15% 0.01 260);
  --color-fg:     oklch(96% 0.005 260);
  --color-accent: oklch(78% 0.17 165);
  --radius:       10px;
  --sp:           1rem;
}

.card {
  background: var(--color-bg);
  color: var(--color-fg);
  border-radius: var(--radius);
  padding: var(--sp);
}

The superpower: change one variable, everything updates. Dark mode is "redefine the same variable names under a different selector":

:root            { --color-bg: white; --color-fg: black; }
[data-theme=dark]{ --color-bg: black; --color-fg: white; }

That's the entire mechanism. No CSS-in-JS required. No build step. A single data-theme attribute on the <html> element flips your whole app.

The mental shift

Before custom properties, theming meant either (a) generating multiple stylesheets at build time, or (b) JavaScript rewriting inline styles. Now it's just CSS. Every design system, every component library, every dark mode toggle in 2026 is built on this.

#2 — `:has()`, the parent selector

For 25 years, CSS could not select a parent based on its children. You couldn't say "a card that contains a video." You used JavaScript. Now you can:

/* a card that has a checked input looks different */
.card:has(input:checked) {
  border-color: var(--accent);
  background: tint(...);
}

/* a form that contains an error gets a red outline */
form:has(.error) { outline: 2px solid red; }

/* a table row with a selected checkbox */
tr:has(input[type=checkbox]:checked) { background: var(--highlight); }

#3 — Container queries

Media queries ask "how big is the viewport?". But often what you actually want to ask is "how big is my container?". A card should look different when placed in a wide sidebar vs a narrow drawer — regardless of the overall window size.

.card-wrapper {
  container-type: inline-size;
}

.card { flex-direction: column; }

@container (min-width: 400px) {
  .card { flex-direction: row; }
}

Grab the bottom-right corner below and drag to resize. The layout inside changes based on the container's width, not the viewport.

Container-aware card

When my parent is wider than 400px, I lay out horizontally. Otherwise vertically. Try resizing the dashed container.

Why this matters

Components should be self-responsive. A card library where each card knows how to lay itself out based on available space is composable everywhere — you drop the card into a 300px sidebar or a 1200px hero and it just works. Container queries are what finally makes "truly reusable components" possible in CSS alone.

#4 — OKLCH, the better color

You've been using hex and rgb and hsl. They all have a problem: they're mathematically convenient but perceptually wrong. HSL's lightness value doesn't match what your eye sees as "lighter" — a yellow at 50% lightness looks way brighter than a blue at 50% lightness.

oklch() fixes that. It's hue/saturation/lightness based on a perceptually-uniform color space. Colors at the same L value look equally bright to your eye.

oklch(96% 0.005 260)   /* near-white */
oklch(78% 0.17 165)    /* teal-green */
oklch(78% 0.17 50)     /* orange — SAME perceptual lightness */
oklch(78% 0.17 280)    /* violet — SAME perceptual lightness */

Six hues, all at L=78% and C=0.17. They look equally bright. Try this with HSL and they won't.

Combine OKLCH with color-mix() and you get magical-feeling color manipulation in pure CSS:

background: color-mix(in oklab, var(--accent) 15%, var(--surface));
/* "15% accent tint on top of surface" — perfect for hover states */

This is used everywhere in the shared stylesheet powering this curriculum. Take a look at shared/styles.css and you'll see this pattern repeatedly. It's how you build a palette from a single hue and get consistent tints.

Bonus: logical properties

Instead of margin-left, use margin-inline-start. In left-to-right languages they mean the same thing — but in right-to-left (Arabic, Hebrew) the logical one flips automatically. If you ever need i18n, you'll thank yourself.

/* old */                 /* new */
margin-left: 1rem         margin-inline-start: 1rem
padding-top: 0.5rem       padding-block-start: 0.5rem
border-right: 1px         border-inline-end: 1px
width: 200px              inline-size: 200px

Not worth refactoring old code for, but use them in new code by default.

Module 1 wrap-up

You now have the mental models you need:
